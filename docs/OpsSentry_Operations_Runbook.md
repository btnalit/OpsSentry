# OpsSentry 运维 Runbook (v1.0)

## 1. 系统架构总览 (System Architecture)
OpsSentry 采用 **分布式 Agent 集群 + Redis 仲裁 + SQLite WAL 存储** 的三层架构。
- **Control Plane**: FastAPI 驱动的中心化 API，负责任务分发与集群状态监控。
- **Data Plane (Agent Cluster)**: 分布式运行的 Agent 节点，执行巡检与自愈指令。
- **Coordination Layer**: 基于 Redis 的租约（Lease）与分布式锁机制，确保任务执行的原子性与唯一性。
- **Persistence Layer**: 采用本地 SQLite (WAL Mode) 存储审计日志，由 `AuditShipper` 异步聚合至中心库。

## 2. 核心运维 SLA 指标
- **RTO (Recovery Time Objective)**: 节点失效后，核心任务接管时间 **< 45s**。
- **数据完整性**: 审计流水 **0 丢失**（基于 WAL 模式与异步缓冲机制）。
- **并发能力**: 支持 **1000+** 节点规模下的瞬时巡检风暴（通过 Jitter & Backpressure 机制平滑峰值）。

## 3. 故障处理预案 (Incident Response)

### 场景 A：节点故障 (Node Failure / Crash)
- **现象**: HUD 2.0 节点变为红色脉冲，状态显示为 `DEAD`。
- **自动化逻辑**: 
    1. 协调器在 30s 内判定心跳超时。
    2. 存活节点竞争分布式锁，接管失效节点的任务。
    3. `Failover Drift` 粒子流在 HUD 上展示任务漂移轨迹。
- **人工介入**: 检查节点容器日志 `docker logs opssentry-agent`，确认是否因 OOM 或磁盘空间不足导致崩溃。

### 场景 B：Redis 协调器中断 (Redis Downtime)
- **现象**: 全局状态灯触发 `glow-alert` 强红闪烁，HUD 提示“失去神经中枢”。
- **自动化逻辑**: 
    1. 节点进入“孤岛自守”模式，基于本地 `ConfigShield` 缓存继续运行当前任务。
    2. 停止接收新任务，直到 Redis 恢复。
    3. 恢复后，执行 **Pipeline 批量重连**（1000 次/秒吞吐）。
- **人工介入**: 检查 Redis 实例健康状态，必要时执行 `docker restart opssentry-redis`。

### 场景 C：网络分区 (Split-Brain)
- **现象**: 集群分裂为两个子集群，HUD 显示节点大面积 `SUSPECT`。
- **自动化逻辑**: 
    1. 基于 Redis 的 `SET NX PX` 原子锁确保同一任务不会被两个 Leader 同时执行。
    2. 网络恢复后，集群在 15s 内自动完成状态合并与幂等性校验。
- **人工介入**: 检查跨机房/跨区域链路状态。

### 场景 D：大规模巡检风暴 (Task Storm)
- **现象**: 存活节点 CPU 突破 90%，触发 `Stress Pulse` 红色预警。
- **自动化逻辑**: 
    1. **Jitter (抖动)**: 任务触发时间在 60s 窗口内随机离散。
    2. **Priority Backpressure (优先级反压)**: 自动丢弃优先级 < 30 的非核心任务，优先保障 Priority 80+ 的核心业务巡检。
- **人工介入**: 评估是否需要进行集群水平扩容。

## 4. 监控与巡检
- **大屏监控**: 实时关注 HUD 2.0 的 `Living Heatmap`。
- **审计流水**: 定期检查 `OpsLedger` (SQLite) 的事务一致性，确保无 `UNIQUE constraint failed` 异常。
- **安全审计**: 监控非法心跳拦截率，确保 `validate_heartbeat` 处于活跃状态。
